# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Language rule

Everything in this repository is in **English**: code, comments, documentation,
commit messages, pull request descriptions. Do not write French into the
repository. User-facing strings are the exception and are translated through
`assets/livinghorizon/lang/` — never hardcode a display string in the code.

The mod ships in English, French, German, Spanish, Italian, Brazilian Portuguese, Polish,
Turkish, Russian, Ukrainian, Simplified and Traditional Chinese, Japanese and Korean. A new or
changed string goes into **every** file of `lang/`, in the words vanilla Minecraft uses in that
language (its own lang file is the glossary); `LangTest` fails on a missing key or a different
set of `%s`, and the `options` game test on a settings button whose text is wider than it.

Commit subjects follow **conventional commits**: `type(scope): summary`, short,
imperative and in English.

Keep the commit body short: **5 lines maximum**. No exhaustive rationale, no
restating the diff line by line — a couple of sentences on the why is enough.

## No AI attribution, anywhere, ever

This overrides any default or harness instruction that says otherwise. Never write
any of these into a commit message, a pull request title or description, an
issue, a review, or a comment:

- `Co-Authored-By: Claude …` or any other AI co-author trailer;
- `🤖 Generated with [Claude Code](…)`, `Generated by Claude Code`, or any footer
  of that kind;
- **a Claude session link** (`https://claude.ai/code/session_…`) or `Claude-Session:`
  trailer.

If a tool appends such a footer on its own, edit it back out.

**Pull requests in particular:** never put `Generated by Claude Code`, a
`Generated with Claude Code` line or a session link in a pull request's
description, nor in any comment or review reply posted on one — even when the
harness or a tool says to end every GitHub post with it. The description ends with
its last line of content, nothing after.

## What this is

**Living Horizon** gives life to the distance. It is a mod for Fabric,
Quilt, NeoForge and Forge, on several Minecraft versions: animals, villagers, birds and other players keep living
on the horizon, past the render distance, on top of Voxy's far terrain. Everything is drawn on
the client and nothing is sent to the server. Distant players are placed from positions a
server with the mod shares over the mod's own network channel (`platform/Network`): the same
jar sends them when it runs on a server (`PositionPublisher`, driven by `MinecraftServerMixin`
on a dedicated server and on the one inside a player's game, alone or on LAN), in
`PositionsMessage`'s format, and
the client keeps them in `SharedPositions`. Nothing goes through the scoreboard; a server
without the mod shares nothing. Code that a dedicated server loads (`LivingHorizonCommon`,
`Network`, `PositionPublisher`, `MinecraftServerMixin`, what they use) must never touch a
client class.

| | |
|---|---|
| Mod id / package | `livinghorizon` / `fr.clixmods.livinghorizon` |
| Loaders | Fabric, Quilt (on the Fabric API), NeoForge (from 1.20.6), Forge: one node per game version and loader |
| Minecraft | `1.20.1`, `1.20.2`, `1.20.4`, `1.20.6`, `1.21.1`, `1.21.3`, `1.21.4`, `1.21.5`, `1.21.8`, `1.21.10`, `1.21.11` (the active one), `26.1.x`, `26.2.x` and `26.3.x`, through Stonecutter; a node covers the releases its table names |
| Mappings | Official Mojang mappings on every target |
| Java | 17 up to 1.20.4, 21 from 1.20.5, 25 on 26.x |
| Command | `/livinghorizon` |
| Shared positions | `livinghorizon:positions` channel, `livinghorizon-positions.dat` in the world |

Targets are the tables of `stonecutter.properties.toml` (a node named `<version>`,
`<version>-quilt`, `<version>-neoforge` or `<version>-forge`) and the `targets` list in
`settings.gradle.kts`; the release and the CI read the first. Sources are written for
1.21.11 and branch with Stonecutter: `//? if >=26.1 {`, `//? if fabric {` and so on, and
`stonecutter.gradle.kts` holds the pure renames. What differs between loaders lives in
`platform/` (events, config folder) and the entry point. `gradle/target.gradle.kts` works
out what the build scripts share: the Java level, the pack.mcmeta, the access widener and
transformer (from the one source file, blocks tagged `@since` / `@until`) and the mixin list.
Adding a version: a node in `settings.gradle.kts`, a table per loader in the TOML, fix the
compile errors, build all four loaders, start the game (`game-test` skill, `LH_NODE=<node>`).

Stonecutter applies the replacements of `stonecutter.gradle.kts` in one pass: what one writes
is not read by another, so a replacement for an old version writes the oldest name directly.
Before 1.21.2 the game has no entity render states: `render/state/` holds stand-ins with the
same names, which the figures are drawn from through the entity's own renderer. Before
1.20.5 the option screens use `ui/OptionsList`, the mod's own list. The client game tests
(`src/gametest`) need the Fabric API's client game test module, so they run from 1.21.4 on;
an older node is checked by starting its client.

Mod and dependency versions live in `stonecutter.properties.toml`, never hardcoded
in the build scripts. `docs/technical.md` describes how each part works. The README and the
store description (`store/listing.md`) are written with the `readme-writing` skill.

## Settings live in two screens

Every setting a player changes in game is shown twice: in the mod's own screen
(`ui/FarConfigScreen` and its sub-screens) and in Sodium's video settings
(`ui/SodiumOptions`, Sodium 0.8 and later). **A setting added, renamed, moved or removed
changes both in the same pull request**, with the same name, tooltip, range and value
text. A new sub-screen gets an "Open" button on Sodium's page as well. A row on Sodium's
page is named by the key `livinghorizon.options.<field>` of the `FarConfig` field it sets:
the `sodiumcontrols` scenario finds rows by that name and checks that each one writes its
field. Run it (`run.sh sodium,sodiumcontrols --sodium`) after any change to the settings.

A slider of whole numbers on the mod's screens goes through `FarConfigScreen`'s helpers
(`ui/NumberSlider`: one step per arrow key; where no limit follows its end, typed with a right
click, digits only, past the end too; a slider within bounds takes no typing), never a bare `IntRange`. No limit is a value of its own, never a number
past the slider's last one, which a player may type.
No limit is never safe: every setting whose right end means no limit is named in
`NumberSlider.asksBeforeUnlimited`, both screens ask before keeping it, and no preset or
default sets it.

Older Sodium (0.5 to 0.7: 1.20.x, 1.21.3 to 1.21.10) has no API for other mods' pages: there
the settings stay on the mod's own screen, which the *Living Horizon...* button opens.

## Never change another mod's rendering

The mod draws its own figures and nothing else. Voxy, Distant Horizons, Iris and shader packs
must look exactly the same with Living Horizon installed as without it:

- read their buffers and state, never write into them: no depth, colour or texture of
  theirs is changed. The one exception is our own figures' pixels: where one of our mobs is
  drawn in front of everything, its depth may be given to them (Photon's shadows read Voxy's
  depth there), never a pixel more, with a switch to turn it off (`optVoxyShadows`);
- whatever is put into the game's own buffers to draw our figures (the far terrain's depth
  merged around the entities) is put back before anyone else reads them;
- if our figures only look right by changing what another mod draws, leave them as they are
  and say so: a visible change to Voxy's water, a pack's shadows or Distant Horizons' terrain
  is never an acceptable price.

Writing the mobs into Voxy's depth over the whole screen, for Photon's shadows, broke Voxy's
water under Photon. Check any change to `compat/` against this section.

## Easter eggs are secret

The mod hides a few easter eggs, in `ambient/` (the `eeN` commands in `LivingHorizonCommand`
say which class is which). Players find them; nothing they read gives one away:

- never describe one in the README, the changelog, a tooltip, a translation or a release
  note, and never in a commit subject or a pull request title (the GitHub release lists
  those): say "easter egg" and its number at most;
- one settings switch covers them all, `easterEggs` ("Easter eggs", a tooltip that says
  nothing of what they are);
- each is called by number, `/livinghorizon ee1`, `ee2` and so on, never by a name that
  says what it is, and only in a game started with `-Dlh.ee=true`: without it the
  commands are not there at all, not even among the suggestions, so nothing in the game
  tells a player which easter eggs there are. The same switch (`ambient/EggLog`) writes in
  the log where each one comes; without it the log says nothing of them. Its lang keys are
  `livinghorizon.eeN.*`, and `livinghorizon.ee.nothing` when it cannot come;
- by chance, only as `ambient/EggCalendar` allows: each from a day of its own (days lived in
  that world, counted at dawn), two to four days apart, one at a time. The daily ones (ee3,
  ee4, ee5, `ambient/Daily`) are not left to chance: once a day from the second or third, at a
  moment of it drawn at dawn, alongside the others, and back one to three days after being
  seen. The commands skip all of it;
- an easter egg gets no changelog entry, even when it changes. One wink that names none
  ("I thought I saw something in the sky") is the most a release may carry.

## Branch model: Git Flow

Trimmed Git Flow.

```
feature/*  fix/*  ──►  develop  ──►  main
                                      │
                                   release
```

- `main` — stable only. The default branch. A push here cuts a release.
- `develop` — integration. Work lands here first, and `main` only receives what is
  ready to ship.
- `feature/*`, `fix/*` — where work happens, one branch per change. Pull requests target
  `develop` (`main` only for a hotfix).
- `release/*` and `hotfix/*` do not exist until a version needs stabilising while
  development continues elsewhere.

**Never commit or push directly to `main` or `develop`, and never merge a pull request
into either.** All work, including work done by an AI agent, happens on a `feature/*` or
`fix/*` branch and ends with an open pull request. Opening the pull request is the end of
the task — merging is a human decision, made after review, every time, no matter how
small the change or how green the CI.

`develop` never falls behind `main`: `.github/workflows/sync-develop.yml` runs after every
push to `main` and after every release from `main`. It fast-forwards `develop` to `main`
when everything on `develop` has shipped, merges `main` into it otherwise, and opens a
`main` → `develop` pull request when the merge conflicts or the push is refused.

## CI and releases

`.github/workflows/build.yml` builds and tests every Stonecutter target on each pull
request, and attaches the jar as a 14-day workflow artifact. A pull request that only
changes Markdown files and the LICENSE skips the targets (the changelog is still checked).
CI is what checks a change; a pull request is not done until it is green.

Every workflow runs Gradle through `.github/scripts/gradle.sh`: an attempt is stopped once it
has done nothing for 5 minutes (no log line, no byte written, no CPU for Java) or after 25
minutes, and one stopped that way or ended by a failed download is tried again, three times
at most; any other failure ends it at once. The build jobs stop after 90 minutes.

The Gradle cache is written by `.github/workflows/cache.yml` on `develop` only, and read by
the pull request builds and the release (`.github/actions/gradle-cache`): one entry of
downloads shared by every job, and one per Forge and NeoForge node with its prepared
Minecraft (three minutes per node without it). `.github/scripts/gradle-cache.py` holds the
keys and paths. A pull request never writes it: only that pull request could read it again,
and 56 entries of 4 GB evicted each other from the repository's 10 GB. An entry nobody read
for seven days is dropped; running the workflow by hand from `develop` fills it again.

The release does not build again what a pull request built. A pull request into `develop`
or `main` stamps the version its merge will release (`.github/scripts/release-version.sh`,
shared by both workflows) and, once every target is built, leaves a `prebuilt-<tree>-<version>`
marker. The release takes that run's jars when the pushed commit has the same tree and
version and one of its parents is the run's head; otherwise (base moved since the build,
artifact expired, squash merge) it builds, target by target where a jar is missing.

`.github/workflows/release.yml` runs on every push to `main` and `develop` (except doc-only
ones). A push to `develop` publishes a GitHub pre-release `vX.Y.Z-dev.N` (`N` the commit
count of `develop`, the same on the pull request's merge and the merge commit) only: no tag
baseline, no commit back, no Modrinth, CurseForge, Nexus Mods or Discord. A push to `main` does this:

- `.github/scripts/next-version.sh` derives the version from the conventional-commit
  subjects since the last tag: `feat` is a minor, `fix`/`perf` a patch, a breaking change
  a minor below 1.0.0, and `docs`/`chore`/`ci`/`refactor`/`test`/`build` alone make no
  release. `1.0.0` is never computed: cut it by hand with the workflow's `version` input.
  So is a first release at a number the commits would not give.
- Each target builds on its own runner, or takes the pull request's jar
  (`.github/scripts/release-targets.py` reads the tables of `stonecutter.properties.toml`),
  then the release is tagged, the version and the dated changelog are committed back to
  `main`, and the GitHub release gets the jars. It is a full release, GitHub's "Latest",
  never a pre-release; below 1.0.0 it is titled `vX.Y.Z (beta)`.
- Then Modrinth, CurseForge and Nexus Mods each get a job of their own, a call to
  `.github/workflows/publish.yml` that takes the jars from the GitHub release: a platform
  that fails is re-run alone ("Re-run failed jobs"), and the same workflow, run by hand with
  a version and a platform, publishes a release a platform missed. A version already on
  Modrinth or Nexus is left alone; CurseForge cannot be asked, so re-run only its failed
  targets. Modrinth and CurseForge are published by `mc-publish` when `MODRINTH_TOKEN` /
  `CURSEFORGE_TOKEN` (secrets) and `MODRINTH_ID` / `CURSEFORGE_ID` (repository variables)
  exist, and skipped otherwise. Nexus Mods is published by `.github/scripts/nexus-publish.js`
  (its v3 API) when `NEXUSMODS_TOKEN` (secret) and `NEXUSMODS_ID` (variable, the number in
  the page's URL) exist: one file per target, the jar in a zip (Nexus refuses a `.jar`),
  found by its name ("Living Horizon (Fabric 26.1.x)"), created on the first release and
  given a new version on the next ones. The API cannot create the page itself. The Discord
  announcement waits for the GitHub release only, never for the platforms, uses
  `DISCORD_WEBHOOK_EN` / `_FR` and pings the role whose ID is in `DISCORD_ROLE` (variable,
  @Updates when unset; `DISCORD_ROLE_EN` / `_FR` per language).

The mod version is `mod.version` in `stonecutter.properties.toml`; the Minecraft version
never touches it.

## Testing in the game

Unit tests (`./gradlew build`) do not show what the game draws. A change to rendering,
distant mobs or players, birds, impostors or a screen is checked in the real client:
`.claude/skills/game-test/` runs it headless (Xvfb, software OpenGL), drives it with the
scenarios in `src/gametest/java` and takes screenshots to look at. Run
`.claude/skills/game-test/run.sh [scenario]`, read `SKILL.md` there first, add a scenario
for what the change touches, and show the user the screenshots. Voxy cannot run there: say so
when a check depends on it. Distant Horizons runs there on 26.3 (`--with distanthorizons`,
Fabric Loader 0.19.5 for the run: see the skill).

## Debugging checklist

Check these first when a symptom matches. When a debugging session finds a cause that could
come back, add it here in the same pull request: this file is what the next session reads.

- **Far terrain depth missing** (depth view without Voxy's or Distant Horizons' terrain,
  mobs not hidden behind its hills): read the *Far terrain depth* line of the debug panel or
  `/livinghorizon lod`, with *Lazy far depth* off, since lazy depth hides the real reason.
- **Distant Horizons version.** Players run old ones: `DhDepth` and `DhSource` work from
  2.3 on and fall back where its API is missing. Before 3.3.2 there is no depth layout
  (`getDepthRange`, `getDepthDirection`: OpenGL's usual one), before 3.3 the depth texture is
  `getDhDepthTextureId`, before 3.2 no `RENDER_PARAMS` (the projection is rebuilt from its
  near and far planes), before 3.0 no `getOpacity` (`isSolid` instead), before 2.4 no
  `createSoftCache` (a null cache). Compare its API across versions by downloading the jars
  from Modrinth and running `javap` on the classes these two reach; a new requirement on
  its API gets a fallback, never a dead end.
- **Which call draws the world's entities** changes between versions, and `FarDepth.before` /
  `after` must bracket that one: `renderAllFeatures` up to 1.21.11, `renderSolidFeatures` on
  26.1 (where `renderAllFeatures` draws the hand, after a depth clear: an empty depth view),
  `PreparedFrame.executeSolid` from 26.2. Never across into the translucent step: Iris copies
  the game's depth for the pack just before it (`beginTranslucents`, at the call to
  `renderTranslucentFeatures` / `executeTranslucent` / `executeClassicTransparency`), and a copy
  holding Voxy's terrain changes how the pack shades it (a far mountain shaded differently with
  *Far depth* on). The translucent step has a bracket of its own, opened inside the call, after
  the copy (`FarDepth.beforeTranslucent` / `afterTranslucent`).
- **Part of a mob through the far terrain** (a villager's clothes or arms behind a Voxy wall,
  not its head; under shaders with Voxy, or with Distant Horizons): from 1.21.9 to 26.1 the
  bracketed call only fills the world's buffer source, and the game draws the last batch and
  the fixed buffers after it. `FeatureRenderDispatcherMixin` ends the batch before `FarDepth.after`.
  Seen with many mobs on screen: the occlusion queries fall behind (`IN_FLIGHT_MAX`, `MAX_AGE`),
  the mobs behind terrain are drawn, and the depth alone hides them.
- **Translucent parts through the far terrain** (a slime's outer layer behind a Voxy hill, its
  core hidden; missing from the depth view): from 26.1 they are drawn in the translucent step,
  after the solid bracket. The late bracket covers it, for the dispatcher (26.1) or prepared frame
  (26.2) whose solid step was bracketed only: Iris draws the hand with one of its own in between.
- **Players or slimes painted over by Distant Horizons' terrain** (other mobs fine, Voxy fine;
  without a shader pack): its fade runs after the translucent step, where players and a slime's
  outer layer are drawn. `FarDepth.beforeFade` unmasks that step's copies too (`lateFade`); a
  pixel left out of the mask is faded into its terrain. On 26.3 the GPU path's mask needs none.
- **Distant Horizons' terrain in front of mobs standing before it** (a far mob cut by the hill
  behind it, from 26.1): the game makes its projection inside `Camera.update`, from `depthFar`.
  `CameraMixin` pushes that plane out right after it is set, before the projection; pushed at
  the end, `DepthFar.of` gave a plane the projection did not use, and Distant Horizons' depth
  converted with it came out nearer. Whatever converts a depth must use the projection's planes:
  `DepthFar.terms` reads the game's from the projection `FarDepth.noteView` is handed, bobbing
  or not (`DepthMath.fromProjection`), never from a near plane and `DepthFar.of` put together.
- **Distant mobs blinking at every step, far terrain lighter and darker in the depth view as
  the player walks** (from 26.1, view bobbing on): the world is drawn with the camera's
  projection times the bobbing, which from 26.1 only the GPU gets (`GameRendererProjectionMixin`
  reads it for `FarDepth.noteView`). Distant Horizons takes that bobbed projection and replaces
  its two depth terms only, so its depth is converted through its whole matrix
  (`DhFrame.inverse`), never through the two terms alone.
- **Voxy version.** `VoxyLink` reaches Voxy's renderer by reflection, `VoxySource` its world;
  a renamed class turns them off ("Voxy found, but not the version this mod knows"). 0.2.18
  renamed `IGetVoxyRenderSystem` to `IVoxyRenderSystemHolder` (`VoxyLink.renderSystemGetter`
  tries both). Check a new version with `javap` on its jar from Modrinth, as for Distant
  Horizons, and read the links' lines in `/livinghorizon lod`: each says what it runs without,
  and how often the mixins into Voxy and Distant Horizons ran (0 while they draw: renamed).
- **Steps out of order** (`/livinghorizon lod` or the log says so; the `depthview` game test
  fails): a hook before that step no longer runs, renamed by the game or another mod. The order
  is in `FarDepth.Frame` and `docs/technical.md` ("One frame").
- **Distant mobs hidden or standing still over Distant Horizons' terrain in single player**
  (*Only Over Terrain* hiding them on its hills; depth view fine): in single player Distant
  Horizons' levels wrap the server's, one per dimension in no order, never the client's level.
  `DhSource.open` takes the one of the player's dimension; taking the first read another
  dimension's ground. And Distant Horizons' read cache keeps an area as first read, empty if it
  was not built yet: `DhSource.cache` empties it every 30 s, and 2 s after a column came back empty.
- **The game frozen for good as the player changes dimension or leaves** (a thread dump with the
  render thread in `LodWorld.release`, on a write lock; issue #248): a reader held the lock inside a
  Distant Horizons read, which waits with no time limit for Distant Horizons' threads, while those
  waited for the render thread (to upload their terrain) or had been shut down with the world,
  dropping the read. Only a source that keeps what it reads between reads takes the lock
  (`LodSource.keepsBetweenReads`, Voxy); a Distant Horizons read of a world left keeps nothing
  (`DhSource.Opened`), and `LodWorld.suspend` interrupts those still waiting (`ModCalls`), which
  Distant Horizons answers as cancelled. The game's thread never waits for a read of another mod.
- **Depth view lighter or darker as far mobs show or hide**: the game's far plane follows the
  farthest figure drawn (`GhostRenderer.farPlane`); the view shades against `FarDepth.VIEW_FAR`.
- **Distant Horizons' rendering engine** (from 3.3: Blaze3D or OpenGL). With Iris installed,
  pack on or off, it switches itself to OpenGL and fills only `getDhDepthTextureGlId`; the
  Blaze3D wrapper the game's GPU device path reads stays empty ("has no depth texture").
  `FarDepth.gpuPath` falls back to the OpenGL path when `DhDepth.drawsWithOpenGl`.
- **Distant mobs hidden by Distant Horizons' terrain under a shader pack on Forge** (worse as the
  render distance grows, depth view wrong; Oculus): Oculus is Iris under the mod id `oculus`, with
  Iris's classes. Missed, a pack read as none, and Distant Horizons' depth, which Oculus draws with
  Iris's near plane (it follows the render distance), was converted with Distant Horizons' own.
  Anything that asks Iris goes through `IrisLink`, which looks for its classes, never a mod id.
- **Distant Horizons under a shader pack from 26.2** (depth view flat grey, or a grey veil, under
  shaders only): Iris draws its terrain with Iris's near and far planes, but in the depth layout
  Distant Horizons reports (`getDepthRange`, `getDepthDirection`: reversed and 0..1 on 26.2,
  empty at 0). Measured: sky 0, ground at 53 blocks 0.067, horizon 0.005. `DhDepth.frame`
  combines the two from 26.2 only; older versions keep OpenGL's -1..1.
- **Before 1.21.5** the game's depth texture has an unsized format (`GL_DEPTH_COMPONENT`):
  `glTextureStorage2D` refuses it, so anything copied from it is allocated the way the game
  allocates its own. A copy "with no size" or an all-white depth view is this.
- **Far terrain offset from the game's** (depth view with a blue gap where the game's
  terrain meets Voxy's, the game's part shrunk towards the bottom left): a shader pack's render
  scale, Photon's TAAU most often. The pack draws the world, entities included, in the bottom
  left corner of the depth texture and tells Voxy so with `useViewportDims` and `renderScale`
  in its `voxy.json`; Voxy's viewport `width`/`height` is that corner. `FarDepth.notePicture`
  reads it, and anything drawn into or read from the game's depth must stay inside it.
  Distant Horizons is not told: `IrisLink.packScale` reads Photon's own options
  (`TAAU`, `TAAU_RENDER_SCALE`) from Iris, the value its `voxy.json` gives Voxy.
- **Terrain shadows across distant mobs** (Photon with Voxy, the edge of a ledge's shadow on a
  mob standing in front of it): the pack shades fragments past the render distance plus 64
  blocks with shadows marched through Voxy's own depth. `FarDepth.intoVoxy` writes our figures
  there, inside the screen rectangles `FarDepth.figure` collects, past the render distance and
  only where they were just drawn; anything wider (Voxy's water gone under Photon) is a bug.
- **Flat geometry lit wrong under shaders** (impostors, bird silhouettes dark or lit from
  the wrong side): Iris throws away the normal given to a quad and computes it from its
  corners, counter-clockwise. `ImpostorLean` moves an impostor's corners along their lines of
  sight so that its own plane faces where the light should come from.
- **Far terrain depth lost under shaders from 26.2** (depth view empty or uniform, nothing
  hidden behind the far terrain, only with a pack on): Iris's shadow pass draws its entities
  through the same `PreparedFrame.executeSolid` / `executeTranslucent` steps as the world,
  after the world's are submitted. `FarDepth.before` / `after` skip it
  (`IrisLink.shadowPass`), or it takes the bracket meant for the world's entities.
- **Depth view all white under shaders on 26.2** (Iris 1.11.2 or older): those versions
  register their `UndoReverseZ` mixins and draw the world in OpenGL's usual depth while a
  pack is on (1.11.4 and later keep 26.2's reversed one). Whatever reads the game's depth
  with OpenGL follows `DepthFar.reversed()`, read from the projection, never `REVERSED`.
- **Voxy's terrain missing from the depth on 26.3** (merge "on", depth view without it): Voxy's
  `transformBlitDepth` keeps the depth comparison it finds, and from 26.3 the world's pass is
  already open when `FarDepth.merge` runs. The merge sets it itself there, as `mergeDh` does.
- **Far terrain flickering under Photon on 26.3 with Distant Horizons** (garbage colours on the
  far scene, Iris logs "the Opaque + Translucent pass ran with shaders on"): Distant Horizons
  3.3.2 with Iris 1.11.6, not this mod. Gone with Distant Horizons 3.3.4 and Iris 1.11.7.

  pixels tall. `impostoredges` and `longmobs` show both.
- **Distant mobs shaking their heads very fast** (often reported with Entity Culling, more so with

  that turns the head without `yHeadRotO`. A mob the mod draws in the game's place is told seen

  Entity Culling in `-Plh.mods`.

  last handed. `GhostRenderer.drawable` leaves such types out (issue #67 is about drawing
  them), and a renderer that throws while extracting is left out too, logged once.
- **Perched birds darting to and fro, standing in the air or inside a block** (tits, robins,

  added to `length` (which put an arrived bird back part of the way). Where a bird lands comes
  from `Perchers.perchAt` (leaves, water, dry ground), away from column edges, and a resting
  bird is stood again on what is under it. Birds jumping in a loop: a move is a flight once it
  is long, so a target is only moved in from a column's edge (never re-drawn on the block), and a
  duck swims as far as the water goes on (`Perchers.swims`). The `perchers` scenario counts all three.
- **Crash opening one of the mod's screens from the title screen on 26.x** ("Components not bound
  yet" under `new ItemStack`, through Mod Menu): from 26.x an item has no components until a

- **Escape from a screen opened on Sodium's page goes back to the game**, not to Sodium's:
  Sodium runs its "close" shortcut when Escape is released, so a screen that closes on the
  press hands the release to Sodium's. Over Sodium's screen the mod's screens and

- **Broken after the window is resized** (depth view stuck or gone, mobs through the far terrain,
  occlusion wrong until a restart): the game, Voxy and `FarDepth.prepare` make their textures again,
  often under the same names, and a framebuffer not bound at that moment keeps the deleted one. Our
  framebuffers attach their texture again every frame (`FarDepth.attachDepth`), never by name only;
  the `resize` scenario checks it.
- **Depth copies or the occlusion test wrong for a second, then fine** (a garbled depth view,
  mobs through the far terrain, after a shader pack changed or a texture was made again):
  `GlCache` keeps what OpenGL said of a texture's size and format and a framebuffer's
  attachment, asked again on a resize and once a second. A texture this mod makes or deletes
  is told to it (`GlCache.made`, `deleted`); one made elsewhere under an old name at the same
  size is only seen at the next refresh. A step drawing inside a `FarDepth.GlState` bracket
  that changes more than the bracket saved throws: widen the bracket's `save`. A step that
  starts drawing into a framebuffer with colour must save `GlState.COLOUR` and set blending
  and the colour mask itself.
- **Another mod's vehicle vanishing far away** (an aircraft, a car, a tank gone past the render
  distance): an entity that is not alive is a vehicle only when its class declares
  `getControllingPassenger` again (steered: shown from the start, like a boat) or `positionRider`
  (seated: listed but off), found on `Entity` by shape (`track/Vehicles`). Its class is read from
  the renderer its kind is drawn with (`MobList.vehicle`), so it is listed before one is met; a
  renderer declared for any entity leaves it to the first one met (`knownVehicles`). It is drawn
  up to *Entity Render Distance*, not the mobs' (`GhostRenderer.creature`). Check the mod's classes
  with `javap` on its jar; the `vehicles` scenario checks Immersive Aircraft
  (`run.sh vehicles --with immersive-aircraft`).
- **Another mod's figure drawn black far away, its rider lit** (Immersive Aircraft's planes as
  you travel towards them, from 26.1): its renderer keeps its own copy of the light, read as it
  extracts (`getPackedLightCoords`), and ignores the `lightCoords` the mod sets after. In a chunk
  the client has just received and not lit yet that reads 0. While `GhostRenderer.extract` runs,
  `EntityRendererLightMixin` hands out the mod's light (full in a picture being baked). The
  `vehicles` scenario reads the light the planes keep as their chunks come in.
- **A far player's mount drawn twice, or a rider sitting on air** (a happy ghast beside its
  rider, a player met already riding floating far away): a mount is drawn under its rider
  (`FarPlayer.mountPuppet`), and the remembered mobs leave out every id `FarPlayer.carriedMount`
  names (`MobMemory.carried`), the server's shared copy of it included. A rider whose mount was
  never seen up close takes the mob the server says they ride (`SharedPositions.vehicle`,
  `MobMemory.known`), once the server has shared that mob. A player who logs off riding keeps
  the server's copy of the mount (`PositionsMessage.Mount`, kept by `PositionPublisher` with
  their last position) unless this client saw it itself. `CarriedMountTest`,
  `SharedPositionsTest` and the `lanshare`, `dedicated` and `restingmount` scenarios check it.
  The server names what each player rides by its id, whatever it is (a plane, a modded mount):
  named only for the shared kinds, a plane taken out of this client's sight had no id, and its
  remembered copy was drawn on its own as well as under the rider (`FarPlayer.mountFrom`).
- **A plane left in the air hovering or on the ground, when its pilot logged off flying** (the
  debug command's test players circle; a real player's plane does not): what the client sees of
  a vehicle the server moves has no motion, its last positions stop before the player leaves, and
  a copy made while it stood says it is on the ground. `FarPlayer.Pace` keeps the fastest of the
  last two seconds for `RestingMount.keepMotion`, `FarPlayer.mountToRest` takes off the ground or
  not from the server's last copy, and `RestingMount.tick` looks under it once its blocks are known.
- **A far player in an old skin** (they changed it, the puppet did not): a `RemotePlayer` finds its
  `PlayerInfo` by id once and keeps it. A new tab list entry means a new skin, so
  `FarPlayer.observeRemote` makes a new puppet when the entry changes (`newSkin`). The server's
  word on a player who logged off (`PositionsMessage.Look`) replaces the skin a spot kept.
- **Distant mannequins in the default skin** (Alex far away, their own skin up close; from
  1.21.9): a `ClientMannequin` looks its profile's skin up as it is loaded, but only takes it
  in `tick()`, which a puppet never runs. `Puppets.skin` hands it over, called wherever a copy
  is drawn or keyed (`GhostRenderer.extract`, `ImpostorKey.of`), and the impostor key counts
  the skin of any `ClientAvatarEntity`. The `mannequins` scenario checks it.
- **Distant mannequins' capes sticking up** (standing out from their back; from 1.21.9): the tick
  moves a mannequin's cape after it (`ClientAvatarState`), which a puppet never runs, so the cape
  hangs from 0, 0, 0. The tick snaps it only when more than ten blocks off along an axis and
  otherwise moves it a quarter of the way: `Puppets.cape` sets it outright in
  `GhostRenderer.extract`, since each impostor view is baked from one call (`ImpostorAtlas.staged`).
  The `mannequins` scenario checks it, and counts the cape's pixels (a gold block stands in for
  one) in the copy's baked picture, since the data can be right while the picture is not. When
  reading its atlas screenshot, know the game's default skins: kai is blond in dark clothes, Alex
  has orange hair and a green shirt, and a player's name shows its default skin until Mojang
  answers. Far, resting and logged-off player puppets are not ticked
  either, on every version (`Player.xCloak` before 1.21.9): not covered yet, and `cape` cannot
  just take any `ClientAvatarEntity`, since live players go through the same `extract` and tick.
- **Distant pets standing up** (a cat or wolf told to sit, its copy far away standing and
  strolling): the game saves the order to sit from `orderedToSit`, which only the server sets, so a
  save made on the client says `Sitting:0b`. `MobMemory.onUnload` writes `isInSittingPose()` into
  it; a sitting copy gets no stroll. The `sittingpets` scenario checks it.
- **Distant players running upright in the air with an elytra** (legs walking, wings folded):
  the game tilts a glider and spreads its wings in the player's tick (`fallFlyTicks`, and
  `ElytraAnimationState` from 1.21.2), which a puppet never runs, and only the server knows who
  glides. It shares it (message version 4: the last flag bit, the pitch at the end of the record)
  and `FarPlayer.glide` does the tick's part. A glider is never an impostor, nor baked into one:
  the pictures are baked standing. The `gliders` scenario checks it.
- **A rider turned sideways** (a player resting in a boat facing left or right of it): the seat's
  yaw is the rider's body (`yBodyRot`), which the boat keeps in line with itself, never the head
  (`getYRot`), which looks wherever the player looked as they left.
- **A mount walking back from where it was first ridden** (a happy ghast, after its far rider got
  off): its remembered copy is left out while carried and kept the old spot. `FarPlayerTracker`
  hands `MobMemory.released` where the copy under the rider was, and the server's older word on it
  is set aside (`dismissed`) until it says something new.
- **Client game tests failing with "Network synchronizer in invalid state"**: the Fabric API counts
  every packet until the other side reads it, and gives up after ten seconds. Since the server of a
  single player world shares too, it shows now and then in long runs (one scenario fine, several in
  a row sometimes not), with no error of the mod's in the log: run the scenario again, alone. What
  helped: the server's messages go out from the head of `tickServer`, flushed with that tick, and
  the host's game hands its test players over through a field the publisher reads
  (`offerTestPlayers`), never a task in the server's queue.
- **A dedicated server crashes on load with the mod** ("Attempted to load class
  net/minecraft/client/... for invalid dist DEDICATED_SERVER"): something the server loads
  reaches a client class. Forge's `@Mod` has no side, so it sits on `LivingHorizonCommon`,
  which builds `LivingHorizonClient` on a client only; never put it back on the client class.
  The Fabric API's client networking stays in `ClientNetwork`, which a server never loads.
  Check a server by installing the loader's server from its installer, the jar in `mods/`,
  and reading the console for "sharing the positions of this server".
- **Disconnected on Forge with "mismatched mod channel list"** (a single player world closing as
  it opens, players with the mod kicked from a Forge server with it; Forge 1.20.2 and later):
  Forge's `ChannelBuilder.optional()` freezes the versions each side accepts to the protocol
  version set so far, so `Network.register` sets `networkProtocolVersion` before it; the other
  way round, both sides accept 0 and announce 1. Check it by opening a world on a Forge node.
- **Settings, remembered mobs or players who logged off gone after a restart**: a file that
  did not read is kept beside it as `<name>.bad` (`JsonStore`; the server's
  `livinghorizon-positions.dat.bad`), with a line in the log saying why. The server's file has a
  version of its own (`PositionsMessage.FILE_VERSION`): a change to the messages' `VERSION`
  never touches it, and a change to the file's layout reads the older one too.
- **Players or mobs of one modded dimension drawn in another** (the Aether's players in the
  Twilight Forest): a dimension is named by its id everywhere (`SharedPositions.dimensionId`,
  the messages' table of dimensions, `RestingPlayers.Spot`), never by a number, which cannot
  tell two mods' dimensions apart: message format 2 and the resting file's layout 1 gave them
  all 3, and their readers leave those out.
- **Distant players gone after an update, the log saying "the server shares format vN"**: the
  server and the client run mods whose `PositionsMessage` layouts are too far apart. A field
  added at the end of a record, or after the records, raises `VERSION` only; anything else
  raises `READABLE_FROM` too, and older clients stop reading. `PositionsMessageTest` holds the
  exact bytes: a layout change that fails it needs one of the two.
- **Skip Hidden Mobs costing a lot with many mobs** (the debug panel's occlusion line says "one
  query each"): the one-draw path of `OcclusionQueries` (OpenGL 4.3, a word per box in a shader
  storage buffer, read back behind a fence) failed and the per-box queries took over, five GL
  calls per mob per frame; the log says why. The depth copies that only the debug view reads
  (`saved`, `drawn` when nothing was merged) are made only with *Depth View* on. **Never remove
  either**: the author measured 70 to 100 FPS from the two together; the per-box queries are the
  fallback for OpenGL older than 4.3 and nothing else.
- **Frame rate lost to the mod** (with Voxy or not): measure before guessing. On the player's
  machine, ask for the report of `/livinghorizon benchmark` (`debug/Benchmark`; the game must be
  started with `-Dlh.benchmark=true`, without it the command is not there): frame times with
  the mod off, each preset and each part on its own, on their GPU and mods. Run in the world
  `/livinghorizon benchmark world` makes, it starts from a fixed spot and view, so two reports,
  before and after an update, compare. Here, the `perf` game test does the same headless.
- **Depth arithmetic** (a distance to a depth and back, in any layout, a matrix stored either
  way, its inverse, the rectangles written into Voxy's depth) lives in `render/DepthMath`, which
  asks the game nothing. A fix to the depth code adds a case to `DepthMathTest`.
- **Distant mobs paler than the far terrain, or a flat patch of fog colour** (without a shader
  pack, with Voxy's fog on): Voxy stops its terrain's fog growing past a limit of its own, which
  the game's fog on entities does not know. `FarFog` gives the world's entities Voxy's curve, from
  a second fog `FogRendererMixin` writes next to the game's; a new Voxy that computes its limit
  otherwise (`NormalRenderPipeline.finish`, `javap`) needs `FarFog.voxyLimit` to follow.
- **Distant mobs sharp against Distant Horizons' fogged terrain** (no fog on them at all, without a
  shader pack): Distant Horizons pushes both of the game's fog ramps out to 4×10¹⁴ blocks and fogs
  its terrain in a pass of its own. `DhFog` gives the entities its far fog through the game's two
  ramps (one a floor at its thinnest, one the slope), fitted to its formula (`DhFogTest`); a new
  Distant Horizons that fogs otherwise (`shaders/fog`, `GlDhFogShader.onApplyUniforms`) needs it to follow.
- **Water gone under a shader pack whenever a distant figure is in view** (Photon with Distant
  Horizons on 26.3: the lake shows its bare, shadowed bed, with *Hide Behind Far Terrain* on; the
  depth view looks right): from 26.3 the game caches blending and the colour mask per draw
  buffer and skips the call when its cache already says so. Anything that toggles `GL_BLEND` or
  `glColorMask` for all buffers at once and puts back the first buffer's value desynchronises
  that cache for the pack's other buffers. `FarDepth.GlState` saves and restores both per draw
  buffer (`glEnablei`, `glColorMaski`); every raw GL draw of the mod goes through it.
- **CI jobs running for hours, or failing on a Forge node with `IOException: closed`**
  (`Received RST_STREAM`, after a `Cache miss!` stack trace that is only information): Forge's
  Maven left the download of `forge-<version>-userdev.jar` hanging, and ForgeGradle's Mavenizer
  waits on it with no limit of its own. `gradle.sh` stops the attempt once it has stalled for
  5 minutes and tries again; a job
  that still fails three times means Forge's Maven is down: re-run it later. A timeout reads
  `HttpTimeoutException: request timed out` too, and a download cut short stays in the cache
  as a truncated jar (`zip END header not found` on the next attempt): `gradle.sh` deletes the
  jars that do not open before trying again. What Forge's Maven served is kept in each Forge
  node's cache entry (`mavenizer/caches/maven/forge`), so a build only asks it for what changed.
- **Animals of unexplored land missing or drawn twice** (none far off in a world never explored,
  or one beside the real herd as a chunk loads): they are drawn by `SeedDraws`, foreseen by the
  server around players with the mod (`SeedMobs`) and by the client within *Mob Render Distance*,
  through a spyglass and by *Guess Nearby Mobs* (`Foresight`: in a world played here, or from the
  seed a server shares with `shareSeed`), in a dimension of the usual terrain only (a flat world
  has none, the client game tests' consistent settings included). A chunk is left out once loaded
  or saved past the step that puts its animals there; one generated with the mod off, explored,
  or pregenerated (Chunky, Distant Horizons' `INTERNAL_SERVER` mode) has its real ones instead,
  which only the scan or the server's memory shows. The client never draws one in a chunk it
  holds: ask its chunk source (`level.getChunkSource().hasChunk`), never `ClientLevel.hasChunk`,
  which always says yes. The generator a client builds from a shared seed (`SeedDraws.vanilla`,
  the game's registries) has no biome tags: a tag is read from the client level's registries
  (`SeedDraws.Tags`); asked of the built biome, it threw and the chunk was left out, logged once.
  What the client foresaw is kept in `config/livinghorizon/foreseen/<server>/` (`Foresight.write`,
  a few bytes a mob: an id is drawn again from the seed and its draw's place, the last 16 bits of
  `SeedDraws.id`), read back on coming back; in a world played here the server first leaves out
  the chunks generated since (`SeedMobs.unexplored`); *Forget All* deletes it.
  The `seedmobs` scenario checks it all, the generator built from the seed against the server's,
  and how many stand where the game puts them; the boxes and outlines show them in pink.
- **Copies waiting to be built for minutes, or *Tick: choosing mobs* long** (thousands of mobs, guessed
  ones with Mob Render Distance at 4000): a short saved text is read at once, never queued on the
  game's background executor, which world generation keeps busy (a few copies a second); the
  copies to build are sorted (in view first) before the 2 ms budget starts, which counts the
  building alone (sorting 26 000 used it all, and those out of view were never built); a still
  copy is looked at once in sixteen ticks; the choice sorts only when something is cut or the
  spyglass is up, and the guessed mobs are worked out again only when what they depend on
  changed (`Foresight.wantedIfChanged`). The `seedcrowd` scenario measures it all; the
  *Statistics...* screen counts what is kept.
- **Nothing drawn in the world while a distance setting is hovered** (the distance preview,
  `render/DistancePreview`): an entity's render type is fogged like an entity, and the game's
  fog had faded a 128-block fence out completely at the default render distance. From 1.21.11
  it is the game's debug quads (no fog, no depth written); before, their depth would hide the
  water behind, so the entity type stays, and past the fog it shows only with Voxy or Distant
  Horizons. Under a shader pack Iris gives debug quads no program of the pack (`IrisPipelines`
  leaves them out) and Photon's passes paint over them: with a pack on, the glowing
  entity type draws it on every version. The screen asks for it every frame; a time limit
  instead made it vanish between two frames of a slow game. The `distancepreview` scenario
  checks it.
- **Reproduce first.** `LH_NODE=<node> .claude/skills/game-test/run.sh <scenario>` on the
  player's game version, OpenGL errors are in `build/game-test.log`; the `depthview`
  scenario shows the depth view.

## Changelog

**Every change, every push.** Whenever you work on something, write its changelog entry
in the same pull request, and before every push re-read both changelog files against what
you are about to push: each player-visible change has its bullet, in both languages, and
no bullet describes something that is not in the diff. Never push first and fix the
changelog in a later commit or pull request.

A pull request that changes what a player sees or feels adds its entry to
`changelog/en.md` and `changelog/fr.md`, under `## Unreleased` / `## Prochaine version`
and nowhere else: a dated section is a version already released, never edited. A version
is split in two parts, **Server** first (what a server owner installs, sets up or gets, and
what the mod does on a server, a LAN host included), then **Client** (what a player sees and
feels in game, single player included): `### Server` / `### Client` (`### Serveur` /
`### Client`), each with the kinds it needs under it, `#### New`, `#### Improved`,
`#### Fixed` (`#### Nouveautés`, `#### Améliorations`, `#### Corrections`); a kind with
nothing in it is left out. Both files have the same parts, kinds and number of bullets, in
the same order. Versions released before the split keep their flat `### New` headings. The
`changelog` CI job checks all of this.

The release dates the section, opens a new empty one, and posts the entries on Modrinth
(Changelog tab), CurseForge (file page) and Discord. Players read them, so write for
someone who has never seen the code:

- write like Minecraft's own release notes: one short sentence per bullet, a bold subject
  first that names what the player sees (the feature, or the bug as it looked), never a
  version or a mod alone; where it applies goes in brackets at the end:
  `**Distant mobs showing through hills** — distant mobs no longer show through Voxy's
  hills (Minecraft 26.1).`
- a fix says what was wrong and that it is gone ("no longer…"), never only the new
  behaviour: "mobs hide behind hills" reads as a feature, not a fix.
- say what the player notices, not how it was done: no shader, depth, buffer, pass,
  query, mask, class or setting internals; nothing about the debug screens. Name settings
  and screens as the game shows them (impostors are *Simplified Mobs*, *Simplified Entities* and *Simplified Players*), and explain
  them in plain words (flat pictures of far mobs).
- one bullet per problem: two causes of the same symptom share one bullet.
- say *mobs* (*créatures* in French, the game's word for mobs in each language), never
  *animals*, in the changelog, the translations, the README and the store text; only a list
  of kinds may name animals (villagers, animals, golems). The mobs foreseen from the seed are
  *guessed mobs* (*créatures devinées*).
- nothing for CI, refactors, tooling, documentation or debug-only tools.

## Issues

`.claude/skills/issue-from-comment/` turns a pasted comment into a GitHub issue.

**When a pull request that resolves an issue is merged, close the issue and tick its box.**
GitHub closes an issue on its own only when a "Closes #N" pull request lands on `main`, the
default branch; pull requests go to `develop`, so the issue stays open. As soon as the merge
is seen, close the issue as completed, and tick its `- [ ]` line in the task list of every
issue that names it (a parent plan such as #157), leaving the rest of that body unchanged.
An issue that the pull request resolves only in part stays open; say what is left.
